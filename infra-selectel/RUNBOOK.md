# Переезд Fattakhov HR на Selectel: порядок работ

Каталог `infra-selectel/` — Terraform и скрипты для Selectel. Каталог `infra/` (Яндекс Облако) не тронут.
Данные не переносим: поднимаем чистую базу, применяем миграции Prisma, заводим владельца.

Статус на момент написания: код проверен **только офлайн** (`terraform fmt`, `terraform validate`, разбор
шаблонов cloud-init и compose, `caddy validate`, сборка стадий Dockerfile). Ни один ресурс Selectel не создавался,
ключей Selectel у нас не было. Всё, что помечено **«не проверено»**, нужно сверить на живом аккаунте.

## 1. Что нужно от владельца и где это хранить

Секреты — **только** вне git: папка `~/.fhr-selectel/` (права 700, файлы 600) на компьютере оператора и копия в менеджере
паролей владельца. В репозиторий (и в чат) ничего из списка не попадает.

1. **Номер аккаунта Selectel** (`selectel_account_id`) — не секрет.
2. **ID проекта** (`project_id`) — из адреса консоли `my.selectel.ru/vpc/<project>/…` — не секрет.
3. **Сервисный пользователь для Terraform** — создаёт владелец в панели: «Управление доступом → Пользователи → Сервисные
   пользователи». Нужны права создавать сервисных пользователей и ключи. Документация показывает роли `member` и
   `iam.admin` в области аккаунта (полный список ролей в документации ресурса не приведён — **не проверено**, какого минимума
   достаточно; если `apply` отвечает «forbidden» — добавить `iam.admin`). Имя и пароль → `selectel_admin_username`, `TF_VAR_selectel_admin_password`.
4. Пароли баз: `TF_VAR_crm_db_password`, `TF_VAR_students_db_password` (разные, генерировать менеджером паролей, 24+ знака).
5. Секреты приложений (`AUTH_SECRET`, `PII_ENCRYPTION_KEY`, `CRON_SECRET`, VAPID, SMTP…) — **прежние** значения со старого
   сервера не нужны, кроме тех, что нельзя менять на живой базе; база пустая, поэтому `PII_ENCRYPTION_KEY` можно сгенерировать
   новый (`npm run keys` в `platform-for-students`) и сохранить в двух местах.
6. Данные почты (SMTP) — см. раздел 15, это блокер.
7. Доступ к Рег.ру (DNS) и GitHub-репозиторию (секреты и переменные Actions).

Файл `~/.fhr-selectel/prod.tfvars` — копия `example.tfvars` с реальными значениями; запуск: `-var-file=$HOME/.fhr-selectel/prod.tfvars`.
Состояние Terraform (`terraform.tfstate`) тоже содержит пароли и ключи открытым текстом — хранить рядом, не коммитить
(`.gitignore` каталога это закрывает). Удалённое состояние в бакете Selectel — `backend.tf.example` (блокировка не проверена).

## 2. Регион ru-6 / зона ru-6c: что подтверждено документацией

Источник: «Доступность продуктов по локациям» и «Отказоустойчивость кластера PostgreSQL» на docs.selectel.ru.

- **ru-6 — мультизональный пул в Москве** (три зоны ru-6a/b/c, дата-центры на расстоянии до 15 км). Для пользователей из Москвы и Казани
  задержка не хуже, чем у Яндекса (ru-central1 — тоже Москва/окрестности). Риска «далеко от пользователей» нет.
- **Сетевые диски в ru-6c:** есть Basic HDD, **Universal SSD v2** (`universal2.ru-6c`) и **Fast SSD v2** (`fast2.ru-6c`).
  Обычных Universal/Fast/Basic SSD в ru-6 нет — поэтому переменная `volume_type` по умолчанию `universal2`.
- **Управляемые БД (в т. ч. PostgreSQL):** в ru-6c доступны (линии Standard/CPU/Memory, HighFreq, Flex). Версия 16 в таблице не
  указана — **не проверено**, проверит `terraform plan` (фильтр `selectel_dbaas_datastore_type_v1`).
- **S3:** в ru-6 есть Standard и Cold (Glacier нет). Адрес `https://s3.ru-6.storage.selcloud.ru` (по шаблону `s3.<пул>.storage.selcloud.ru` из документации), регион в запросах `ru-6`.
- **Группы безопасности:** доступны в ru-6.
- **Облачные серверы — РАСХОЖДЕНИЕ С ЗАДАНИЕМ.** В таблице для ru-6 линия **«Standard» не отмечена ни в одной зоне**, а у
  ru-6c отмечены «Standard с выделенными ядрами», HighFreq, HighFreq с выделенными ядрами, 10G Net, GPU. Владелец пишет, что в
  консоли выбрана линия standard, — значит, таблица может отставать от панели. **Перед `apply` в панели открыть создание
  сервера в ru-6c и посмотреть, какие конфигурации 2 vCPU / 4 ГБ предлагаются и сколько стоят.** Если «Standard» нет — выбрать
  равную по цене линию (с выделенными ядрами / HighFreq) и записать `flavor_id` готовой конфигурации в `prod.tfvars`; тогда
  Terraform не создаёт свою конфигурацию. Какая линия получится у конфигурации, созданной Terraform-ом (`disk = 0`, по образцу
  Selectel), — **не проверено**.
- **Container Registry и плавающие IP** в таблице не перечислены (она их не содержит). Реестр работает на общем адресе
  `cr.selcloud.ru` (из документации ресурса); если реестр в проекте не создаётся — раздел 5.1.
- В момент проверки статус-панель Selectel показывала инцидент «Unavailability in the ru-6 pool» (по данным поиска; на
  момент запуска работ перепроверить `selectel.live`).
- Один узел БД в ru-6: SLA (99,95 % запись) относится только к кластерам с репликами; без реплики при отказе мастера база
  недоступна до его восстановления, данные не теряются. Для старта согласован один узел (`db_node_count = 1`); реплика —
  `db_node_count = 2` (вдвое дороже).

Если окажется, что какого-то сервиса в ru-6 нет, его создают в другом пуле: серверам и БД нужна **одна** сеть/пул, поэтому
переносить надо всё сразу — выставить `region`/`zone` (в документации Selectel встречаются пулы ru-3, ru-9 и др.; где они находятся и есть ли там
S3 и DBaaS, проверять по той же таблице доступности). Если пул окажется не московским, задержка для пользователей из Москвы и Казани вырастет на единицы–десятки миллисекунд —
для этих приложений обычно некритично (не измерялось);
S3 в другом пуле (`s3_pool`) добавляет задержку только на загрузку/выдачу файлов.

## 3. Как запускать Terraform

Terraform не установлен на компьютере — запуск в Docker (из каталога `infra-selectel`, Git Bash):

```bash
export MSYS_NO_PATHCONV=1
alias tf='docker run --rm -it -v "$(pwd -W)":/w -v "$HOME/.fhr-selectel":/secrets -w /w \
  -e TF_VAR_selectel_admin_password -e TF_VAR_crm_db_password -e TF_VAR_students_db_password \
  hashicorp/terraform:latest'
tf init
tf plan -var-file=/secrets/prod.tfvars -out=/secrets/prod.tfplan
tf apply /secrets/prod.tfplan
```

(Если нужен `deploy.sh` — ему нужен Terraform на самом компьютере или `terraform output -json` в файл; проще поставить
бинарник Terraform ≥ 1.5.)

**Загрузка провайдеров.** При проверке 16.10.2026 `terraform init` с `registry.terraform.io` из этого окружения прошёл
(selectel v7.8.1, openstack v2.1.0, aws v5.100.0, random v3.9.1; хэши в `.terraform.lock.hcl`), но загрузка `aws` один
раз оборвалась («unexpected EOF») — повторить. Если реестр недоступен совсем: скачать архивы провайдеров с
`releases.hashicorp.com` / страниц релизов, положить в локальное зеркало (`terraform providers mirror`, затем
`provider_installation { filesystem_mirror { path = "…" } }` в `~/.terraformrc`). Файл блокировки в git — чтобы версии не
менялись сами.

## 4. Порядок переезда (начисто)

**Шаг 1. Сервисный пользователь Terraform** (раздел 1, п. 3). Проверить вход: `tf plan` не должен падать на аутентификации.

**Шаг 2. Репозиторий.** Ветка `infra/selectel` (не вливать в `main`, пока не согласовано).

**Шаг 3. Проверки до создания ресурсов в панели:**
- линия и цена конфигурации 2 vCPU / 4 ГБ в ru-6c (раздел 2);
- имя образа ОС: `openstack image list` или панель; в `variables.tf` имя **собрано по образцу** документации
  («Ubuntu 24.04 LTS 64-bit») — не проверено, поправить `image_name`;
- версия PostgreSQL 16 и тип диска БД (`db_disk_type`: по документации ресурса допустимы `local` и `network-ultra`);
- квоты проекта (vCPU 4, ОЗУ 8 ГБ, диски 80 ГБ, 2 плавающих IP, 1 DB-кластер).

**Шаг 4. Первый `apply` — в несколько заходов** (провайдеры `openstack` и `aws` настраиваются значениями из ресурсов,
которых ещё нет, поэтому создаём их по очереди):

```bash
tf apply -var-file=/secrets/prod.tfvars \
  -target=random_password.project_user -target=random_password.s3_crm_user -target=random_password.s3_students_user \
  -target=selectel_iam_serviceuser_v1.project -target=selectel_iam_serviceuser_v1.s3_crm \
  -target=selectel_iam_serviceuser_v1.s3_students -target=selectel_iam_s3_credentials_v1.crm \
  -target=selectel_iam_s3_credentials_v1.students -target=selectel_vpc_keypair_v2.main
# затем сеть и плавающие адреса — они нужны для DNS (шаг 5)
tf apply -var-file=/secrets/prod.tfvars \
  -target=openstack_networking_floatingip_v2.server -target=openstack_networking_router_interface_v2.main
tf output app_ip students_ip
```

Если на первом заходе `terraform` жалуется на неизвестные значения провайдера — это ожидаемо, повторить после появления
сервисного пользователя. (Не проверено на живом аккаунте.)

**Шаг 5. DNS (до серверов!).** Caddy выпускает сертификаты Let's Encrypt при первом запуске и ему нужны записи на новые
адреса. В Рег.ру (раздел 7) прописать A-записи на `app_ip` / `students_ip`. Яндекс сейчас лежит, параллельной работы нет,
поэтому переключать можно сразу, а не «в окно».

**Шаг 6. Реестр, токены, образы (раздел 5):** `apply` реестра и токенов, настройка секретов GitHub, сборка четырёх образов.

```bash
tf apply -var-file=/secrets/prod.tfvars -target=selectel_craas_registry_v1.main \
  -target=selectel_craas_token_v2.server -target=selectel_craas_token_v2.ci
```

**Шаг 7. Остальное:** `tf plan`, прочитать, `tf apply`. Создаются база, бакеты, серверы. Cloud-init на каждом сервере ставит
Docker, входит в реестр и запускает `fhr-stack.service` (`docker compose up -d`): миграции → приложение → Caddy. Если образов в
реестре ещё нет, служба повторяет попытку раз в минуту.

**Шаг 8. Адрес базы.** Проверить `tf output db_connections`: в Terraform хост берётся из ключа `master` карты `connections`
(в документации ресурса ключи не описаны — **не проверено**). Если хост взялся не тот, поправить `local.db_host` в
`compute.tf`, `apply` и `./deploy.sh all` (пересоздавать серверы не нужно).

## 5. Образы, реестр, CI

Образы собирает GitHub Actions: **Образы для выкатки (Selectel)** (`.github/workflows/images-selectel.yml`; прежний
`images.yml` для Яндекса не тронут). Один образ — один запуск, тег **новый**.

Настройки репозитория (Settings → Secrets and variables → Actions):

| Что | Значение | Откуда |
| --- | --- | --- |
| Variable `SELECTEL_REGISTRY` | `cr.selcloud.ru/<имя реестра>` | `tf output registry_endpoint` |
| Secret `SELECTEL_REGISTRY_USER` | логин токена записи | `tf output -raw registry_ci_username` |
| Secret `SELECTEL_REGISTRY_TOKEN` | токен записи | `tf output -raw registry_ci_token` |
| Variable `DB_CA` | `none` (по умолчанию) или `file` | раздел 12 |

Теги и цели сборки (из workflow): `fhr-crm` (CRM, цель `runner`), `fhr-crm-tools` (CRM, цель `tools`: миграции, worker,
owner-bootstrap), `fhr-students` (платформа, цель **`runner`**), `fhr-students-tools` (платформа, цель `tools`: миграции,
`admin:create`). Все четыре нужны. Команда локально (на ARM-ноутбуке медленно, поэтому через Actions):
`docker buildx build --platform linux/amd64 --target runner --build-arg DB_CA=none --build-arg APP_URL=… crm`.

Теги образов — в `prod.tfvars` (`crm_tag` и т. д.); токены доступа к реестру живут в состоянии Terraform, токен только
чтения ещё и в cloud-init сервера.

**Docker Hub.** Серверу нужны `caddy:2-alpine` и `alpine:3.20` с Docker Hub. Из российских сетей Hub бывает нестабилен
(лимиты, блокировки). Запасной вариант: один раз положить эти образы в свой реестр (`docker pull`, `docker tag`,
`docker push cr.selcloud.ru/<реестр>/caddy:2-alpine`) и указать `caddy_image`, `cron_image` в `prod.tfvars`. **Не проверено.**

### 5.1. Если реестра Selectel нет / не создаётся

Запасные варианты: (а) реестр GitHub Container Registry (`ghcr.io`) с read-токеном на серверах — образы остаются
в зарубежном сервисе, для ПДн это допустимо (в образах ПДн нет), но доступность `ghcr.io` из РФ нестабильна; (б) свой реестр
на отдельной ВМ. Для (а): удалить `registry.tf`, `registry_endpoint` заменить на `ghcr.io/<owner>`, логин/токен — переменными.

### 5.2. Сертификат БД в Dockerfile (минимальная правка кода)

Dockerfile обоих приложений скачивал корневой сертификат Яндекса с `storage.yandexcloud.net` при каждой сборке: во время
аварии Яндекса сборка могла упасть, а сертификат Selectel другой. Добавлен аргумент сборки `DB_CA`: `yandex` (по умолчанию,
поведение прежнее), `file` (файл `certs/db-ca.pem` из контекста: `crm/certs/db-ca.pem`, `platform-for-students/certs/db-ca.pem`)
или `none`. Workflow Selectel по умолчанию собирает с `none`. Проверено: стадии `db-ca` собираются во всех трёх режимах.

## 6. Миграции, владелец, администратор платформы

Миграции на пустую базу накатываются **сами**: сервис `migrate` (CRM) и `students-migrate` (платформа) выполняют
`npx prisma migrate deploy` перед стартом приложений. Вручную (на сервере, `ssh ubuntu@<ip>`):

```bash
# CRM (сервер fhr-app)
sudo DOCKER_CONFIG=/root/.docker docker compose -f /opt/fhr/docker-compose.yaml run --rm migrate
# платформа (сервер fhr-students)
sudo DOCKER_CONFIG=/root/.docker docker compose -f /opt/fhr/docker-compose.yaml run --rm students-migrate
```

**Владелец CRM.** Сервис `owner-bootstrap` на каждом запуске стека выполняет `npx tsx scripts/bootstrap-owner.ts ensure`:
на пустой базе создаёт организацию «Fattakhov HR Agency» и приглашение для `profattakhov@gmail.com`, отправляет письмо со ссылкой
**один раз** (факт записан в базе). **Нужна рабочая почта** (`SMTP_URL`, `SMTP_FROM` в `crm_env`). Ссылка нигде не печатается.
Повтор вручную: `sudo … docker compose -f /opt/fhr/docker-compose.yaml run --rm owner-bootstrap`; проверка почты без
отправки: `… run --rm owner-bootstrap npx tsx scripts/bootstrap-owner.ts send --dry-run`. Не запускать `scripts/setup-real.ts` —
он стирает базу.

**Администратор платформы.** Роль ADMIN входит только через CRM; запись заводится сама при первом входе из CRM. Заранее:

```bash
# на fhr-students
sudo DOCKER_CONFIG=/root/.docker docker compose -f /opt/fhr/docker-compose.yaml run --rm students-migrate \
  npm run admin:create -- hr@fattakhovhr.ru
```

Пароля у такой учётной записи нет. Остальное для платформы (справочник вузов `load-institutions`, ключи) — по
`platform-for-students/ЗАПУСК.md`; тестовые данные (`db:seed`) на боевую базу **не накатывать**.

## 7. DNS в Рег.ру

Сейчас записи ведут на адреса Яндекса. Нужно изменить **A-записи** (предварительно, за сутки до работ, снизить TTL до
300 с; при нынешней аварии можно менять сразу):

| Имя | Тип | Куда | Примечание |
| --- | --- | --- | --- |
| `fattakhovhr.ru` (@) | A | `app_ip` | сайт |
| `www` | A (или CNAME на @) | `app_ip` | |
| `my` | A | `app_ip` | кабинет |
| `students` | A | `students_ip` | платформа |

Не менять: MX, TXT (SPF/DKIM/DMARC) — они зависят от почтового провайдера (раздел 15). AAAA-записей на старые IPv6-адреса
не оставлять (у нас только IPv4). Записи CAA, если есть, должны разрешать `letsencrypt.org`.

**Что должно быть готово до выпуска сертификатов:** DNS уже отдаёт новые адреса; порты 80 и 443 открыты (группа `fhr-app`);
`maintenance_mode` корректен; Caddy видит рабочий контейнер. Проверка: `docker logs` контейнера `caddy` без ошибок ACME. Лимит
Let's Encrypt — 5 неудачных проверок в час на имя: до готового DNS серверы не запускать.

## 8. Проверка работоспособности

```bash
curl -fsS https://my.fattakhovhr.ru/api/health            # {"ok":true}
curl -fsS https://my.fattakhovhr.ru/api/health/worker     # 200, пока фоновый процесс жив
curl -fsS https://students.fattakhovhr.ru/api/health
curl -fsSI https://fattakhovhr.ru/ | head -3              # 200 и HSTS
```

Руками: вход владельца по ссылке из письма; загрузка файла в кабинете (проверка S3); загрузка видео в платформе (проверка
CORS бакета и подписанных ссылок); письмо сброса пароля (проверка почты). Логи: `ssh ubuntu@<ip>`, `sudo docker compose -f /opt/fhr/docker-compose.yaml logs --tail 100 app`.
Если `/api/health` даёт 503 — приложение не достаёт до БД: смотреть `DATABASE_URL`, группу безопасности `fhr-db`, TLS (раздел 12).

## 9. Откат

- **Образ приложения:** вернуть прежний тег в `prod.tfvars` → `tf apply` → `./deploy.sh app` (или `students`).
- **Конфигурация/окружение:** `git revert` + `tf apply` + `./deploy.sh`. Серверы не пересоздаются: `user_data` игнорируется.
- **Страница технических работ:** `maintenance_mode = "on"` → `apply` → `deploy.sh` (перезапуск Caddy — секунды).
- **Целиком обратно на Яндекс:** возможно только когда Яндекс вернётся; данные в Selectel начисто не переносятся, поэтому
  вернуться без потери данных, внесённых после переезда, нельзя. До первых реальных данных откат — вернуть A-записи.
- **База:** точка во времени в пределах **7 суток** (ограничение блока `restore` в документации ресурса) или из резервной копии (раздел 11).

`deploy.sh` ходит по SSH, поэтому на время выкатки в `ssh_allowed_cidrs` вписывается свой адрес (`["x.x.x.x/32"]`), после — снова `[]`
и `apply`. Если SSH закрыт, а нужен срочно, — консоль сервера в панели Selectel.

## 11. Резервное копирование

- **PostgreSQL:** автоматические копии включены на стороне Selectel; срок хранения — `db_backup_retention_days = 30`
  (аргумент `backup_retention_days`). Время окна копий и поведение при одном узле в документации ресурса не описаны —
  **проверить в панели** после создания. Проверку восстановления делать раз в квартал по образцу `infra/README.md`: восстановить
  в отдельный кластер (блок `restore`: `datastore_id` + `target_time`, не далее 7 суток), сверить число строк, удалить кластер.
- **S3:** репликации (Replication) и жизненного цикла в S3 Selectel **нет** (документация API). Версионирование защищает от
  случайного удаления/перезаписи, но не от потери бакета. Предлагаемая копия: раз в сутки `rclone sync`/`aws s3 sync` в
  бакет другого пула или у другого провайдера (на ключе только чтения). Не настроено — решение владельца.
- **Серверы** без данных, кроме тома `caddy_data` (сертификаты, переиздаются автоматически): копировать не нужно. Конфигурация —
  в git и в состоянии Terraform.
- **Состояние Terraform и `prod.tfvars`** — копия в менеджере паролей владельца (иначе при потере пароли баз придётся менять).

## 12. TLS к базе

В Яндекс-версии сертификат кластера лежал в образе (`NODE_EXTRA_CA_CERTS`), строка подключения была с `sslmode=require`.
Сертификат управляемой БД Selectel и способ проверки в доступной документации **не найдены** — **не проверено**. Порядок:
1. После создания кластера открыть его в панели, скачать корневой сертификат (если он есть), положить в
   `crm/certs/db-ca.pem` и `platform-for-students/certs/db-ca.pem`, поставить переменную репозитория `DB_CA=file`, пересобрать образы.
2. CRM подключается драйвером `pg` (Prisma 7, `@prisma/adapter-pg`): в актуальных версиях `sslmode=require` трактуется как
   `verify-full`, и без своего CA соединение может падать с ошибкой сертификата. Варианты в `db_sslmode`:
   `require` (по умолчанию), `require&uselibpqcompat=true` (шифрование без проверки цепочки, как в libpq), `verify-full`
   (нужен CA и совпадение имени хоста). Если БД подписана публичным центром — свой CA не нужен.
3. Платформа (Prisma-движок): `sslmode=require` шифрует, `sslaccept=strict` включает проверку по системному набору (в
   Dockerfile платформы сертификат из `db-ca.pem` кладётся в системное хранилище).
Решение «шифруем без проверки» (`uselibpqcompat`) допустимо только внутри частной сети проекта и должно быть осознанным.

## 13. Удаление персональных данных и версии объектов

В Яндексе правило жизненного цикла удаляло неактуальные версии через 30 дней (угроза T19: удалённое по требованию субъекта
резюме не должно жить прошлой версией). В S3 Selectel Lifecycle не поддерживается. Приложение при удалении файла вызывает
обычный `DeleteObject` (без `VersionId`) — это маркер удаления, а не стирание. Значит, **с `bucket_versioning = true` удалённые
резюме остаются в бакете навсегда**, пока их не удалить явно. Варианты:
- (по умолчанию) версионирование включено, раз в сутки — `scripts/s3-prune-versions.sh <бакет> 30 --apply` (cron; сначала без
  `--apply`);
- `bucket_versioning = false` — нет копий и нет защиты от перезаписи, зато удаление окончательное. Решение владельца с
  юристом. Выбранный вариант записать в журнал мер защиты ПДн.

## 14. S3: что отличается от Яндекса

- Эндпоинт `https://s3.ru-6.storage.selcloud.ru`, регион `ru-6` (имя пула). **Код приложений менять не нужно:** клиенты S3 в
  CRM (`crm/lib/storage/s3.ts`) и платформе (`platform-for-students/lib/storage.ts`) берут всё из переменных окружения
  `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`. Жёстко заложены только `forcePathStyle: true`
  (Selectel поддерживает адресацию по пути; по документации API она — вариант по умолчанию) и **значение по умолчанию региона
  `ru-central1`**, которое перекрывается переменной `S3_REGION` (Terraform её задаёт; без неё подпись запросов не сойдётся).
- Бакет создаётся через провайдер `aws` (в провайдере Selectel такого ресурса нет). Провайдер при обновлении читает много
  настроек бакета, часть которых S3 Selectel не поддерживает (ACL, Lifecycle, шифрование, теги…) — возможны ошибки `NotImplemented`.
  **Не проверено.** Запасной путь: `manage_buckets = false`, бакеты создать в панели (адресация «по пути» — вариант по умолчанию;
  в документации сказано, что переключить адресацию после создания бакета нельзя), версионирование и CORS платформы
  (разрешённые методы PUT/GET/HEAD, origin `https://students.fattakhovhr.ru`, заголовок ETag) включить там же, имена записать в
  `bucket_*_name`.
- Серверного шифрования (SSE-KMS) в списке поддерживаемых операций нет. Для 152-ФЗ выяснить у Selectel, шифруется ли
  хранилище на их стороне; при необходимости — шифрование на стороне приложения.
- Изоляция ключей CRM и платформы **не гарантирована** (комментарий в `project.tf`): проверить и при необходимости ограничить
  политиками бакетов.

## 15. Почта и SMS — зависимости от Яндекса, которые надо решить

- **SMTP.** И CRM, и платформа шлют письма через Yandex Cloud Postbox (`SMTP_URL=smtps://…@postbox.cloud.yandex.net:465`). Пока
  Яндекс лежит, писем нет — а от них зависят **вход владельца (приглашение), сброс пароля, оповещения**. Код работает с любым
  SMTP (меняются `SMTP_URL`, `SMTP_FROM`). Нужен другой провайдер (российский сервис рассылки или почта домена на Рег.ру, откуда
  уже идут оповещения) и новые SPF/DKIM-записи в DNS. Это **блокер** для `owner-bootstrap`: без почты ссылку входа владелец
  не получит. Выбор провайдера — решение владельца; в Selectel отдельного почтового сервиса в проверенной документации нет.
- **SMS-коды** (`crm/lib/notifications/sms.ts`): жёстко заложен адрес Yandex Cloud Notification Service
  (`https://notifications.yandexcloud.net/`, регион ru-central1). Без ключей `SMS_*` способ «по телефону» на экране просто
  отсутствует (так задумано в коде), поэтому на первое время ключи не задавать. Замена провайдера SMS — отдельная доработка кода
  (в этот PR не входит).
- **Яндекс.Метрика** подключается скриптом в браузере — не зависит от серверов, остаётся.

## 16. Открытые вопросы и допущения

1. Линия серверов в ru-6c (Standard нет в таблице, а владелец видит её в консоли) — раздел 2.
2. Имя образа Ubuntu 24.04 в Selectel и версия PostgreSQL 16 в ru-6 — не проверены.
3. Роли сервисного пользователя Terraform — не проверены (раздел 1).
4. Ключи карты `connections` кластера, порт (допущен 5432) и тип диска БД в ru-6 — не проверены.
5. Бакеты через провайдер `aws`: совместимость с S3 Selectel при `apply`/refresh — не проверена; запасной путь есть.
6. Корневой сертификат БД и режим `sslmode` — раздел 12.
7. Почтовый провайдер вместо Postbox и замена SMS — раздел 15.
8. Изоляция бакетов между приложениями (политики) и шифрование хранилища для 152-ФЗ.
9. Версионирование бакетов против удаления ПДн — раздел 13 (решение владельца).
10. Готовы ли платить за второй узел БД (SLA), мониторинг Selectel в панели, резервную копию S3 в другое место.
11. Реестр `cr.selcloud.ru` в проекте/ru-6 — не проверен (раздел 5.1).
12. Блокировка состояния Terraform в бакете Selectel — не проверена.
13. Допущено: обычный `terraform apply` не пересоздаёт серверы (`user_data` игнорируется); смена окружения/compose
    идёт через `deploy.sh`. Смена `user_data` «по-настоящему» = `-replace` сервера (потеряются сертификаты Caddy и выпуск
    повторится: лимит Let's Encrypt 5 в неделю на имя).

## 17. Риски

- Всё проверено только офлайн: первый живой `apply` почти наверняка потребует правок (имена образов/конфигураций, роли, ключи
  `connections`).
- Один сервер на приложение и один узел БД: отказ сервера/мастера — простой до восстановления; SLA только для кластера с репликами.
- Секреты (пароли БД, ключи S3, токены реестра) лежат в состоянии Terraform и в `user_data` серверов (видны пользователям
  проекта с доступом к серверам). Защита — закрытое состояние и ограничение круга доступа.
- Без почты (раздел 15) владелец не войдёт в CRM.
- Docker Hub и `registry.terraform.io` из России нестабильны — зеркала/запасные образы (разделы 3, 5).
- Инцидент в пуле ru-6 на момент проверки статус-панели (раздел 2).
